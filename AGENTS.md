# AGENTS.md — orientation for AI agents (and humans) new to this repo

Read this first. It is the shortest path to a correct mental model of the
project. `docs/architecture.md` is the file-by-file map; `readme.md` is the
deep narrative on *why* the code is shaped the way it is (each weird bit there
is a measured disaster).

## What this project is

A zero-dependency Node 20+ (ESM) tool called **ff091126** that:

1. **Scrapes** fantasy-football data from a small set of sources: FantasyPros
   MyPlaybook (the user's own leagues on ESPN/Yahoo/Sleeper), FantasyPros
   public pages + API v2 (current-week + rest-of-season rankings/projections
   only — no other weeks), Draft Sharks (current-week + rest-of-season only),
   VegasEdge (current week only: sportsbook-props projections re-scored here
   from the stat line, plus its simulated p10–p90 spread, boom/bust and skew;
   brought back 2026-10-23 for the spread, shown beside the agreed number and
   never counted in it),
   the ESPN NFL schedule, two demand signals (Yahoo BuzzIndex, Sleeper
   trending) that are not projections, and Dynasty Daddy (one request for its
   player rows — ids, ADP and the ESPN/FanDuel/FantasyGuys ROS ranks — plus
   each Sleeper/ESPN league's full schedule). Dynasty Daddy's ~20 trade-value
   markets were fetched once and deliberately dropped: a market value is a
   price already shaped for someone else's league, and pricing for each
   league is League Value's job. Other sources (WinWithOdds,
   First Down Studio, FanDuel, Sleeper/Yahoo weekly projections) and the
   cross-source "consensus" blend were deliberately removed — see git history
   if you need to understand why.
2. **Joins** everything onto a row-per-player universe (`src/enrich.js`) into `data/enriched.json`.
3. **Builds** a single self-contained `dist/dashboard.html` from
   `src/dashboard.template.html` (`src/dashboard.js`). The dashboard runs
   fully in-browser off an inlined JSON payload.

There is **no build step for the app** — `dist/dashboard.html` is generated by
`npm run dashboard` (or `sync`). No dependencies are installed or shipped.

## Commands you will actually run

```sh
npm test                 # node --test, no deps. Run after ANY change.
npm run status           # per-source freshness + the parallel "site's own clock"
npm run sync             # fetch stale sources, then enrich + dashboard + audit
npm run sync -- --only trend,buzz   # named steps (or a preset: live, projections, leagues); joins still run
npm run log              # the permanent run log (data/runlog.jsonl)
npm run dashboard        # rebuild dist/dashboard.html from data/enriched.json
npm run serve            # local server (http://localhost:4173): Sync, Log, league switches work
npm run all              # sync --force
```

All commands are wrappers over `src/cli.js`; `node src/cli.js help` lists them.
Do not hand-roll fetches against the undocumented MyPlaybook API to "test"
something — use `--dry-run` (`npm run sync -- --dry-run`) instead.

## Architecture in one glance

```
data/latest.json  ───────────────►  fetch steps (per-source syncs write data/<source>/)
        ▲                                  │
        │                                  ▼
   (per-league scrape)            src/enrich.js  joins EVERYTHING
                                        │
                                        ▼
                                 data/enriched.json
                                        │
                                        ▼
            src/dashboard.js renders src/dashboard.template.html → dist/dashboard.html
```

- Pipeline orchestration lives in `src/sync.js`: `steps()`, `runPipeline()`,
  and `pipelineMods()` — the ONE wiring of step names to sync functions. The
  CLI and `serve.js` both call it; do not give either its own copy (the
  server's drifted and silently lost four steps).
- **Projections + rankings are fetched one way each.** FantasyPros: `fpSync`
  (public pages, then the API supplement when a key is set). Draft Sharks:
  `dsSync` (current week + ROS). No alternate modes, no per-week flags.
- **Every sync line goes to the run log** (`src/runlog.js`, `data/runlog.jsonl`).
  A step's `run` gets `{ season, week, log }`; print through that `log`, not
  `console.log`, so the dashboard's Log page and toasts see it.
- **Freshness decides fetches.** `src/freshness.js` is a single ledger
  (`data/freshness.json`) recording *when we fetched* and *when the source
  itself last recomputed* (they are different clocks, and conflating them was a
  real bug). Each source has a `MAX_AGE_MIN`; a step younger than its limit is
  skipped. Joins (`enrich`, `dashboard`, `audit`) are exempt from `--only` and
  always run.
- **Data means one thing per row.** `buildUniverse` in `src/dashboard.js` builds
  one row per player; every page and the per-source Sources pages read the
  same row (`buildSourceTables`). Never "re-join" data by reading the
  per-source files a second time — that is a defect that actually shipped.
- **No consensus, no cross-source blending — with ONE sanctioned method.**
  Each source (FantasyPros, Draft Sharks, each expert ROS rank) is shown
  as its own number, current week + rest of season only. Do not add per-week
  data beyond the current week (My Team's Schedule tab lists the opponents
  for the weeks left: schedule, never a projection). The exception is **League Value**
  (`src/leaguevalue.js`), asked for explicitly: it combines sources, but only
  their *within-position order* (ranks, never values — each source's values
  assume a different league), then prices that order with this league's own
  projection curve and replacement level. The same method, without the
  league's replacement level (`lvConsensus`), is the **agreed** week and ROS
  number every player table shows (position rank + points), asked for
  explicitly. Rest of season the position rank is the order of the totals
  (per-game rate × games left), and with a league open it is League Value's
  order, so ROS rank, Value and the "#" overall rank never disagree. Inputs are FantasyPros and Draft Sharks only, ONE vote per site
  split across that site's signals (`src/valuescale.js` `vsSignals`); market
  trade values are not inputs, and ESPN/FanDuel/FantasyGuys ranks are shown
  for comparison, never counted. It is always shown beside the
  sources it came from, with its inputs visible on the player card. Do not add
  a combined number by any other method, and do not average values anywhere.

## Conventions (follow these so the code stays coherent)

- **No dependencies, ever.** The project deliberately has none. Node built-ins
  and the platform `fetch` only. Adding a package is a large, load-bearing
  decision — ask first.
- **No comments unless they explain a "why".** Docblocks at the top of files are
  the norm and are expected; mid-file comments should earn their keep (bugs,
  measurements, measured trade-offs). Do not add restatements of the code.
- **Every fix ships as a regression test.** Tests in `test/` are mutation-checked:
  each pins a defect that actually shipped. Reintroducing the bug must fail a
  test. Run `npm test`; add a test alongside any behavior change.
- **`data/`, `.env`, and `dist/` are gitignored.** League keys and cookies are
  credentials. Never log, print, or commit them. Test fixtures must not require
  real league data.
- **The dashboard template embeds a ~5,000-line inline `<script>`** that never
  runs under Node. CI does `node --check` on the extracted blocks; run that if
  you touch `src/dashboard.template.html` (see `.github/workflows/test.yml`).
- **Dashboard type comes from tokens.** Font sizes are the `--fs-*` scale in
  the template's stylesheet; an uppercase label joins the one "eyebrow" rule
  rather than setting its own size and tracking. Buttons are `.btn`
  (`.primary`, `.danger`, `.sm`). Page titles get their where-you-are eyebrow
  from `render()`, not from each page.
- **Tables, lists and data cells follow `docs/components.md`** (proposed;
  being migrated to). New tables pick DataGrid / Table / List by the data's
  shape and declare columns by `kind`, rather than adding another `*Cell`
  helper or a hand-built `el('table')`.
- Source files are ES modules with named exports. Node 20+ (`node --test`,
  `fetch`, `AbortSignal.timeout`). No npm lockfile; CI runs bare `npm test`.

## Where things live

| Path | What |
|---|---|
| `src/cli.js` | CLI entrypoint + command dispatch table |
| `src/sync.js`, `src/freshness.js` | pipeline runner + step wiring + freshness ledger |
| `src/runlog.js` | the permanent run log every sync writes and the dashboard shows |
| `src/enrich.js` | the join: FantasyPros + Draft Sharks onto rosters |
| `src/dashboard.js`, `src/dashboard.template.html` | dashboard build + in-browser app (pages, command palette, toasts, Log/Sync/All Leagues) |
| `src/weekhorizon.js` | pure logic, inlined into the page (look-ahead window labelling) |
| `src/dynastydaddy.js` | Dynasty Daddy: player rows in one request (ids, ADP, ESPN/FanDuel/FantasyGuys ROS ranks — no trade values) + `league/load` (schedule, potential points) |
| `src/powerrank.js` | pure logic, inlined into the page: contender / trade-value team scoring, tiers, needs, schedule strength |
| `src/leaguevalue.js` | pure logic, inlined into the page: `lvConsensus` — the agreed position order and points for a window (no league) — and League Value on top of it: this league's ROS points curve → value over replacement (real roster depth, halfway between last starter and waiver) |
| `src/sourcefeeds.js` | pure logic, inlined into the page: the Sources pages — one page per site, one tab per file that site gives us (FantasyPros week/projections/ROS/trade/points/news, Draft Sharks boards and stat lines, Dynasty Daddy player data, Yahoo buzz, Sleeper trending + actuals, ESPN schedule), each read off the universe rows with its file path and ledger clock |
| `src/valuescale.js` | pure logic, inlined into the page: the week and ROS sources a row answers for — FantasyPros and Draft Sharks as inputs (one vote per site, `vsSignals`), ESPN/FanDuel/FantasyGuys ROS ranks for comparison only — feeding the agreed numbers, League Value and the Values/Power Rankings columns. The page puts them on one axis with leaguevalue.js `lvWorth` (a source's position rank, priced for the league) |
| `src/fpsync.js`, `src/scrapefp.js`, `src/fpapi.js`, `src/draftsharks.js` | the two projection/ranking sources |
| `src/vegas.js` | VegasEdge (needs `VEGAS_TOKEN`): this week's QB + flex boards and the boom/bust batch, three requests a sync. Points are scored from the stat line (`scoreLine`) because the site's own figure follows the account's saved scoring |
| `src/leaguestate.js` | league on/off state + the account's full league directory |
| `src/buzz.js`, `src/sleepertrend.js` | demand signals (not projections) |
| `src/actuals.js` | weekly fantasy points for every player who played (Sleeper stats). Not a projection. The page uses these when a matchup lineup has no score |
| `src/serve.js` | `npm run serve` server |
| `data/` | all scraped + derived data (gitignored) |
| `test/` | `node --test` regression suite — mutation-checked |
| `docs/architecture.md` | file-by-file code map (what each module reads/writes, callers) |
| `readme.md` | the full narrative: every source, every decision, every zero-dependency rationale |
